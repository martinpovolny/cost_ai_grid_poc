# Data Retention — Cost Event Consumer

This document covers which PostgreSQL tables grow continuously, the recommended
retention window for each, the expected storage impact by event rate, and the
SQL procedures and autovacuum settings required to enforce the policy.

---

## Tables That Grow Unboundedly

| Table | Purpose |
|---|---|
| `raw_events` | One row per ingested CloudEvent. Stores the full JSON body plus receive timestamp and routing metadata. Used for audit logging, event replay, and debugging ingestion failures. |
| `metering_entries` | One row per metered resource-period. Generated by the metering sweep at ~3 rows per source event. Carries `rated_at` once the rating engine has processed the entry; unrated rows drive the rating queue. |
| `cost_entries` | One row per cost calculation output. Generated at ~3 rows per source event; represents the monetary value attributed to a metering entry under a specific cost model. Forms the basis of all cost reports. |
| `wallet_ledger_entries` | One row per ledger transaction (debit or credit) against an account or wallet. Produced when cost entries are settled. Required for financial reconciliation. |

None of these tables have a built-in TTL or partition drop mechanism. Without a
retention policy their sizes grow indefinitely.

---

## Retention Policy by Table

| Table | Recommended retention | Reason |
|---|---|---|
| `raw_events` | 90 days | Sufficient for incident investigation and event replay; CloudEvent sources re-emit on request for longer windows |
| `metering_entries` | 13 months | Covers a full calendar billing year plus one month overlap for month-boundary reconciliation |
| `cost_entries` | 7 years | Financial accounting obligation under most jurisdictions (e.g. IRS 6-year rule, EU 7-year requirement) |
| `wallet_ledger_entries` | 7 years | Financial record; required for audit and customer dispute resolution |

## Storage Sizing by Event Rate

Row sizes used in the projection:
- `raw_events`: 500 bytes/row, 1 row per event
- `metering_entries`: 220 bytes/row, 3 rows per event
- `cost_entries`: 270 bytes/row, 3 rows per event
- **Total effective cost per event**: ~1,970 bytes

| Rate | 1 day | 1 week | 1 month | 1 year |
|---|---|---|---|---|
| 100 events/min | 270 MB | 1.8 GB | 7.9 GB | 96 GB |
| 1,000 events/min | 2.6 GB | 18.5 GB | 79 GB | 964 GB |
| 10,000 events/min | 26 GB | 185 GB | 793 GB | 9.4 TB |

At 1,000 events/min sustained for one year, `raw_events` alone accounts for
~245 GB. Pruning it at 90 days reduces that contribution to ~60 GB, recovering
~185 GB (~19% of total DB size).

Run `./scripts/analyze-sizing.sh` against a running instance to get
projections calibrated to the observed event rate.

## Cleanup SQL

Run cleanup during low-traffic periods. Always delete in bounded batches to
avoid row-level lock escalation and to keep WAL growth predictable.

### raw_events (90-day TTL)

```sql
-- Delete in batches of 10,000; repeat until 0 rows deleted
DELETE FROM raw_events
WHERE received_at < NOW() - INTERVAL '90 days'
  AND id IN (
    SELECT id FROM raw_events
    WHERE received_at < NOW() - INTERVAL '90 days'
    LIMIT 10000
  );

VACUUM ANALYZE raw_events;
```

### metering_entries (13-month TTL)

Only prune entries that have already been rated — unrated entries may still be
in the processing queue regardless of age.

```sql
DELETE FROM metering_entries
WHERE period_end < NOW() - INTERVAL '13 months'
  AND rated_at IS NOT NULL
  AND id IN (
    SELECT id FROM metering_entries
    WHERE period_end < NOW() - INTERVAL '13 months'
      AND rated_at IS NOT NULL
    LIMIT 10000
  );

VACUUM ANALYZE metering_entries;
```

### cost_entries (7-year TTL)

```sql
DELETE FROM cost_entries
WHERE cost_date < NOW() - INTERVAL '7 years'
  AND id IN (
    SELECT id FROM cost_entries
    WHERE cost_date < NOW() - INTERVAL '7 years'
    LIMIT 10000
  );

VACUUM ANALYZE cost_entries;
```

### wallet_ledger_entries (7-year TTL)

```sql
DELETE FROM wallet_ledger_entries
WHERE created_at < NOW() - INTERVAL '7 years'
  AND id IN (
    SELECT id FROM wallet_ledger_entries
    WHERE created_at < NOW() - INTERVAL '7 years'
    LIMIT 10000
  );

VACUUM ANALYZE wallet_ledger_entries;
```

Wrap each DELETE loop in a cron job or a Kubernetes CronJob that retries until
the row count drops to zero, then runs VACUUM ANALYZE. A reasonable schedule is
nightly at 02:00 UTC.

## Autovacuum Tuning for High-Churn Tables

PostgreSQL's default autovacuum thresholds (20% dead-tuple fraction) are too
conservative for `raw_events`, which receives a continuous insert stream and
will be deleted in large batches. Tighten the thresholds so the table stays
lean:

```sql
ALTER TABLE raw_events SET (
  autovacuum_vacuum_scale_factor  = 0.01,   -- vacuum when 1% of rows are dead
  autovacuum_analyze_scale_factor = 0.005   -- analyze when 0.5% of rows changed
);
```

Apply similar settings to `metering_entries` if the unrated queue grows to
millions of rows before the rating sweep clears it:

```sql
ALTER TABLE metering_entries SET (
  autovacuum_vacuum_scale_factor  = 0.02,
  autovacuum_analyze_scale_factor = 0.01
);
```

These settings persist across restarts and do not require a reload.

## Future: Table Partitioning

The current schema uses unpartitioned heap tables. Once any of the following
thresholds is reached, the batch DELETE approach becomes expensive:

- `raw_events` > 50 million rows
- `metering_entries` > 50 million rows
- `cost_entries` > 50 million rows

At that scale, switch to range partitioning by month using
[`pg_partman`](https://github.com/pgpartman/pg_partman). Partition drops are
O(1) catalog operations — they avoid the WAL amplification, table bloat, and
lock contention that large DELETEs produce on unpartitioned tables.

Recommended partition granularity:
- `raw_events`: monthly (90-day retention → 3 live partitions)
- `metering_entries`: monthly (13-month retention → 14 live partitions)
- `cost_entries`: yearly (7-year retention → 7 live partitions)
- `wallet_ledger_entries`: yearly (7-year retention → 7 live partitions)

This is not implemented yet. Track progress in `docs/decisions/` if a partition
migration ADR is opened.

## Monitoring Growth

The consumer exposes two Prometheus metrics for tracking table growth:

| Metric | Labels | Description |
|---|---|---|
| `cost_consumer_db_table_rows_total` | `table` | Live row count per table (from `pg_stat_user_tables.n_live_tup`) |
| `cost_consumer_db_table_size_bytes` | `table` | Total relation size in bytes (data + TOAST + indexes) |

Recommended alerts:

- **Warning**: `cost_consumer_db_table_size_bytes{table="raw_events"} > 50e9`
  (raw_events exceeds 50 GB — partitioning recommended)
- **Warning**: `cost_consumer_db_table_rows_total{table="metering_entries"} > 50e6`
  (metering table is large enough that batch deletes will be slow)
- **Critical**: unrated queue depth `> 100,000` for more than 10 minutes
  (rating pipeline is falling behind ingestion rate)

Import the Grafana dashboard at `deploy/observability/grafana/dashboards/cost-consumer.json`
to visualise these metrics alongside the event ingestion rate.
